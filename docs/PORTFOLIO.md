# 如何把项目转化为可解释的作品集

不要把尚未完成的实验写成成果，也不要把工具辅助生成的代码当作自己已经掌握的知识。先运行、修改、解释，再在简历中描述你实际理解并参与的工作。

## 五分钟演示顺序

1. 展示一次英文文本搜图，指出排名高但位置或数量不符的结果。
2. 打开提示词对比，解释逐模板归一化与集成方式，而不是只展示分数变化。
3. 打开实验记录，解释 nDCG、多正例 recall、bootstrap 统计单位和一个失败切片。
4. 展示模型指纹检查及原子索引构建，说明工程细节如何影响实验可信度。
5. 坦诚说明合成集、单检查点和 CPU 的限制，提出下一步验证计划。

## 可以讨论的技术问题

| 问题 | 你需要能解释的内容 |
|---|---|
| 为什么有时检索到颜色不对的圆？ | 全局语义表示、合成域与细节辨别；单个案例不证明原因 |
| CLIP loss 如何构造？ | 批内 N×N 图文相似度、双向交叉熵、温度与负例假设 |
| 为什么不展示“97% 置信度”？ | 相似度不等于校准概率，softmax 依赖候选集 |
| Hit@K 和 Recall@K 有何区别？ | 单正例等价、多正例不同；给一个具体例子 |
| 提示词集成提升可靠吗？ | 配对差值、组重采样、区间包含 0、测试集不可调参 |
| 为什么不先用向量数据库？ | 当前规模精确搜索可控，消除近似误差；扩展时再测 ANN |
| 怎样证明两次运行可比较？ | 同一数据和查询摘要、权重、预处理、精度与指标定义 |
| 部署瓶颈是什么？ | 模型启动/内存、序列化推理、请求排队、上传与代理限制 |

## 基于当前证据的简历表述草稿

> 实现 CLIP 多模态检索与评测工作台，支持图文融合、提示词消融与可追溯索引；建立多正例检索指标、分组 bootstrap 和失败切片分析，并完成 48 图/108 查询组合诊断集上的真实预训练模型实验。提供 FastAPI 服务、Docker 配置与自动化测试。

只有你能够解释和复现这些内容后，才适合采用该表述。不要添加“自研大模型”“SOTA”“大规模线上”“M1 GPU 加速”或未经验证的性能提升。

## 更有价值的下一步

1. 在有许可的自然照片子集上冻结协议并重复实验，比较合成与自然域差异。
2. 运行另一预训练 checkpoint，保持图库、指标与硬件一致；分析训练数据与架构差异的混杂。
3. 添加独立人工标注的空间关系/否定/数量难例，避免只验证生成器定义的模式。
4. 有明确失败模式后再尝试轻量适配器，分离训练、开发和测试，不用测试标签构造原型。

这比单纯扩大代码量或添加未经验证的复杂模块更能支持技术讨论。
